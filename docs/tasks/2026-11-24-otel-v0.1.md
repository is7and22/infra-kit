# OTel 追蹤元件第一版：Collector 設定、nginx 模組片段、trace 串接檢查、Python 包法

主題歸：mini-16（協調 session 名稱，回報與提問用 SendMessage 傳給它）
角色：backend（只動本 repo）

## 一句話

本 repo 的第一個元件 `otel/`：讓各項目不寫初始化程式就能把一個請求在 OpenObserve 串成一條 trace。第一個接入的是 faninsights（另一張單，等本單打 tag 後開），所以本版只放 faninsights 驗得到的部分：Collector、nginx 官方 OTel 模組、串接檢查、Python 零程式注入。Node、nginx 只改設定的版本、Celery、ansible role 留到下一個項目再加。

## 已經做完

- repo 骨架：README（公開 repo，禁放客戶資料）、dev-checks pre-commit（含公開 repo 的禁字檢查）
- 設計已定（見協調紀錄）：
  - 應用一律用 OpenTelemetry 零程式注入（`opentelemetry-instrument` 等啟動器），以 `OTEL_*` 環境變數設定，應用不寫初始化程式
  - 每台主機（本機開發則每個 compose）一個 Collector，應用只送本機 Collector，由它轉送 OpenObserve
  - 入口 nginx：能連外安裝的環境用 nginx 官方 `ngx_otel_module`
  - 整個 repo 一個版本號，項目以 tag 引用；打 tag 由協調決定

## 這一步要做

1. `otel/README.md`：約定，給項目照填
   - 服務名：`OTEL_SERVICE_NAME` = `<項目>-<服務>`；同一映像跑不同角色各取一個
   - `OTEL_RESOURCE_ATTRIBUTES` 帶 `service.version`（映像 tag）與 `deployment.environment.name`（`dev`／`test`／`prod`）
   - 應用端環境變數清單：`OTEL_EXPORTER_OTLP_ENDPOINT` 指本機 Collector、`OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`、`OTEL_METRICS_EXPORTER=none`、`OTEL_LOGS_EXPORTER=otlp`、`OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED=true`
   - 項目怎麼引用本 repo：git submodule 掛在 `vendor/infra-kit`，指到 tag
2. `otel/collector/`：Collector 設定範本
   - 收 OTLP gRPC 與 HTTP；`memory_limiter`、`batch`；送 OpenObserve 用 `otlphttp`
   - OpenObserve 位址與認證只從環境變數讀（例：`OPENOBSERVE_OTLP_ENDPOINT`、`OPENOBSERVE_AUTH`），檔案裡沒有任何值
   - 附一段 compose 服務範例。映像用 `otel/opentelemetry-collector-contrib`，釘到兩週以上的確切版本
3. `otel/nginx/`：官方模組片段
   - http 層片段：`otel_exporter` 指 Collector 的 gRPC、`otel_service_name`、`otel_trace on`、`otel_trace_context propagate`（已帶 `traceparent` 的請求沿用，沒有就新起）
   - `load_module` 只能放 main 層，片段 include 不到：README 寫明項目要在 nginx.conf 頂端加哪一行
   - README 寫明含模組的官方映像 tag（先查 Docker Hub 官方 nginx 映像有沒有 `-otel` 變體，例 `nginx:<版本>-alpine-otel`；沒有就停下來回報）
4. `otel/check/check_trace.py`：串接檢查，只用標準函式庫
   - 參數：OpenObserve 位址、認證（從環境變數讀）、trace id、期望出現 span 的 `service.name` 清單、期望出現帶該 trace id 的 log 的 `service.name` 清單、等待上限秒數
   - 輪詢查 traces 與 logs，全部到齊結束碼 0；逾時結束碼 1，列出缺哪個服務的 span 或 log
   - 可以被 import 成函式，也可以當命令列跑；faninsights 會在自己的整合測試裡呼叫
5. `otel/python/README.md`：Python 零程式注入包法
   - 套件：`opentelemetry-distro`、`opentelemetry-exporter-otlp-proto-http`，加 `opentelemetry-bootstrap -a requirements` 列出的 instrumentation，釘版本
   - 啟動：原指令前加 `opentelemetry-instrument`（gunicorn、uvicorn、celery 各一例）
   - 已知要注意的：gunicorn 多 worker 不必 `post_fork`（SDK 的批次處理器在 fork 後自己重建），但不開 `preload_app`、指標關掉；某一層已由框架內建的 OTel 中介層開 span 時，用 `OTEL_PYTHON_DISABLED_INSTRUMENTATIONS` 關掉重複那層，否則另起一棵樹；用到沒有 instrumentation 的 HTTP 客戶端時，要在程式裡自己 `propagate.inject`
6. CI（GitHub Actions）：
   - `check_trace.py` 的測試
   - Collector 範本用 `otelcol-contrib validate` 驗過（帶假的環境變數值）
   - nginx 片段放進第 3 步查到的映像，加上 `load_module` 跑 `nginx -t`

實際路徑：項目以 submodule 取本 repo 的 tag → compose 用 `otel/collector/` 起 Collector、入口 nginx include `otel/nginx/` 的片段 → 應用照 `otel/python/` 啟動 → 項目的整合測試呼叫 `otel/check/check_trace.py` 到 OpenObserve 查
寫入端：不適用（本 repo 沒有資料）。OpenObserve 裡的 trace 與 log 由各項目應用與 nginx 經 Collector 寫入，在 faninsights 那張單驗
驗收分派：全部由執行者自驗，輸出貼進進度；打 tag 由協調在你併 main 後決定
手冊：不適用（沒有終端使用者介面）

## 驗收

1. `check_trace.py` 的測試用標準函式庫起一個假 OpenObserve：三個服務都有 span 與 log 時結束碼 0；拿掉其中一個服務的 span，結束碼 1 且訊息點名那個服務；拿掉 log 同理。突變：把「全部到齊」的判斷改成「任一個到」，測試要紅
2. Collector 範本 `otelcol-contrib validate` 通過；拿掉 `OPENOBSERVE_AUTH` 的引用、改成寫死字串，禁字或測試要能抓到（說明你用哪一條抓）
3. nginx 片段在第 3 步的映像裡 `nginx -t` 通過；拿掉 `load_module` 那行，`nginx -t` 失敗。兩次輸出貼進進度
4. GitHub Actions 全綠，`pre-commit run --all-files` 綠

## 最容易漏的地方

- 公開 repo：範例值一律用 `192.0.2.0/24`、`example.org`、`<項目>` 這類保留值。從 faninsights 或其他項目抄設定時，帳號、網域、OpenObserve 組織名都要換掉。禁字檢查只擋幾種常見的，擋不到的不會有錯誤訊息
- `load_module` 寫進 http 層的片段，`nginx -t` 會失敗；但項目若沒跑 `nginx -t` 直接 reload，舊設定會繼續跑，看起來正常，其實模組沒載入、沒有任何 span
- Collector 設定裡的環境變數語法是 `${env:NAME}`；寫成 `$NAME` 不會報錯，送出時拿到的是字面字串，OpenObserve 回 401，Collector 只在 log 印錯，應用端看不到
- `otel/python/README.md` 寫的是 faninsights 會照做的事，寫錯會直接變成那張單的錯。不確定的寫「待 faninsights 驗證」，不要寫成定論

## 不要做

- 不改 faninsights 或其他項目
- 不打 tag
- 發現非改不可的設計問題（例如官方 nginx 映像沒有 otel 變體）就停下來回報，不自己換做法
